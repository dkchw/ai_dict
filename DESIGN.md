# Design Philosophy & Architecture: AI Dict

This document explains the **why** behind AI Dict's design decisions — the deep thinking process, core principles, architectural philosophies, trade-offs, security considerations, and potential conflicts that guide the project. It is intended for contributors, autonomous agents, and developers who need to understand the project deeply before extending or refactoring it.

## 1. The Core Philosophy

### 1.1 "Language Learning is a Personal, Long-Term Journey"

Traditional online dictionaries and translation tools are fundamentally **stateless**:
1. You encounter an unfamiliar word or sentence.
2. You look it up in a browser tab or pop-up.
3. You read a static definition or a mechanical translation.
4. You close the tab.
5. Two days later, you encounter the same word, have forgotten it, and repeat step 1 from scratch.

This interaction paradigm is broken for serious language learners. Language acquisition is non-linear and cumulative. A learner does not just need a definition; they need to understand:
- **Nuance and Connotation:** How does this word differ from its near-synonyms?
- **Context and Register:** Is this formal, literary, colloquial, or obsolete?
- **Etymology and Morphology:** What roots, prefixes, or compound elements explain why this word means what it means?
- **Retention and Active Recall:** How do I review this word repeatedly until it becomes part of my active vocabulary?

AI Dict was conceived to invert the traditional model:

| Dimension | Traditional Dictionary / Translation | AI Dict Philosophy |
|---|---|---|
| **Data Storage** | Ephemeral or cloud-siloed | Local SQLite, permanent, owned by the user |
| **Lookup Result** | Static, pre-compiled text | Context-aware Markdown generated by modern LLMs |
| **Follow-up** | Impossible or resets context | Inline conversational inquiry with memory |
| **Multi-Entry Context** | Tabs vanish on reload | History persists, queryable, taggable, exportable |
| **Privacy & Telemetry**| Tracked queries, ad-supported | 100% local database, zero tracking, zero telemetry |
| **Speed vs. Depth** | Fast but shallow, or slow and deep | Dual-track: Instant offline MT + Deep LLM inquiry |

## 2. Core Architectural Principles

### 2.1 Local-First, Always

**All user data lives on the local machine.**
- The database is stored in the user data directory:
  - **Linux:** `~/.local/share/ai_dict/ai_dict.db`
  - **macOS:** `~/Library/Application Support/ai_dict/ai_dict.db`
  - **Windows:** `%APPDATA%\ai_dict\ai_dict.db`
- There are no user accounts, no cloud sync servers, no telemetry, and no centralized databases.
- The user can inspect the database directly using `sqlite3` or any GUI tool.
- A one-click backup creates a timestamped `.zip` containing the SQLite database.

**Trade-off Rationale:** We deliberately trade away out-of-the-box cross-device cloud sync in exchange for absolute privacy, zero operational cost for the user, offline reliability, and data durability.

---

### 2.2 The Dual-Track Strategy: Fast Offline MT vs. Deep LLM Inquiry

A core breakthrough in AI Dict's design is resolving the tension between **lookup speed** and **explanation depth**:

1. **Track 1: Machine Translation (MT) — Fast, Free, Offline:**
   - Powered by Meta's **NLLB-200** (600M distilled, int8 quantized) executed locally on the CPU via **CTranslate2**.
   - Zero API cost, sub-second latency, fully functional with zero internet connection.
   - Supports 200+ languages via Flores-200 codes (`eng_Latn`, `deu_Latn`, `fra_Latn`, `vie_Latn`, `zho_Hans`, etc.).
   - Used for quick reading, sentence comprehension, and instant subtitle translation.

2. **Track 2: Large Language Model (LLM) — Nuanced, Interactive, Deep:**
   - Powered by top-tier LLMs via OpenRouter (e.g., Claude 3.5/3.7, DeepSeek V3/R1, GPT-4o) or local Ollama.
   - Provides deep etymology, grammatical breakdown, cultural register, example sentences, and comparative analysis.
   - Supports multi-turn follow-up conversations directly within the entry.

**The "Escalation" Pattern:** In both the Web UI and the Browser Extension, users start in fast, lightweight MT mode. If the translation requires deeper understanding, a single click "escalates" the text to the LLM without losing state.

---

### 2.3 The Zero-Memory Contract for Ephemeral Lookups

A critical design rule for the Browser Extension:
> **Default Machine Translation lookups in the browser extension MUST NOT pollute the user's permanent dictionary history unless explicitly requested.**

When browsing the web or watching a video, users look up dozens of incidental phrases that they have no desire to retain long-term (e.g., UI labels, navigation buttons, transient dialogue). If every selection was saved to SQLite:
- The database would be overwhelmed with low-value junk data.
- Spaced repetition decks would be polluted with meaningless fragments.
- Profile history would lose its curation quality.

Therefore:
- Extension MT calls send `save_history: false` by default.
- Users can click a "Save to History" or bookmark color button if they wish to persist an entry.
- Full LLM searches (which represent intentional learning efforts) are saved to the active profile.

---

### 2.4 One-API-Call-Per-Mode (Cost & Latency Control)

For primary lookups (Search, Compare, Explain, Translate, Correction), the backend makes **exactly one LLM API call**:
- No multi-agent loops.
- No iterative tool-calling chains.
- No recursive reflection prompts during initial query.

**Why:** Agentic loops introduce high latency (5–15 seconds) and variable API costs. High-quality single-shot results are achieved through **rigorously engineered system prompts** that instruct the model to produce exhaustive, structured Markdown in one pass.

Follow-up chat is the only multi-turn interaction, streaming subsequent tokens while maintaining previous context.

---

### 2.5 Markdown as the Universal Data Interchange

All AI responses are generated, transmitted, and stored as raw GitHub-Flavored Markdown:
- **Portability:** Markdown can be rendered anywhere (React frontend, terminal CLI, future mobile apps).
- **Human Readability:** Direct SQLite inspection reveals readable text, not opaque serialized JSON payloads.
- **Structured Extraction via Regex:** Rather than forcing the LLM into strict JSON mode (which often degrades its literary and pedagogical explanation quality), the system prompt instructs the model to include standard metadata markers:
  ```markdown
  * **Language**: French
  * **Base form (lemma)**: courir
  ```
  The backend parses these with regex (`re.search(r'\*\*Language:?\*\*:?\s*([^\n]+)', content)`). If prompt formatting changes, the parser in [`ai.py`](file:///run/host/home/dkchw/Documents/Code/Ongoing/Repo/AI_Dict/src/ai_dict/ai.py) must be updated in tandem.

---

### 2.6 Profiles and Sessions: Hierarchical Organization

To prevent cognitive clutter, learning data is organized in two tiers:

1. **Profiles (Namespaces):**
   - Independent learning environments (e.g., *"German C1"*, *"Medical Terminology"*, *"French Fiction"*).
   - Scopes all history queries, active models, system prompts, and external link templates.
   - Deleting a profile cascades to delete its associated entries, keeping SQLite clean.

2. **Sessions (Temporal Clusters):**
   - Every lookup within a profile is tagged with a `session_id`.
   - Defaults to the ISO date string (`YYYY-MM-DD`), automatically grouping daily study.
   - Users can create named Study Sessions (e.g., *"Chapter 4 Grammar"*, *"Goethe Institute Prep"*) and reassign entries between sessions.

---

### 2.7 The Learning Loop: Active Recall via Flashcards

Accumulating dictionary entries is useless without active recall. AI Dict includes a comprehensive **Spaced Repetition Flashcard System** ([`FlashcardTab.jsx`](file:///run/host/home/dkchw/Documents/Code/Ongoing/Repo/AI_Dict/frontend/src/components/FlashcardTab.jsx)):
- **Card Generation:** Automatically turns stored words, comparisons, and explanations into study decks.
- **Card Structure:** 
  - Front: Word term / phrase, language indicator, star rating, color bookmark.
  - Back: Full AI Markdown explanation, follow-up notes, collocations.
- **Ergonomics:**
  - 1-column vs. 2-column spread layouts.
  - Instant flip vs. 3D card flip animation toggles.
  - Fullscreen distraction-free mode.
  - Keyboard-driven workflow (`Space`/`Enter` to flip, `ArrowLeft`/`ArrowRight` to navigate, `ArrowUp`/`ArrowDown` to advance).

### 3.2 The Extension Integration Architecture

The browser extension ([`extension/`](file:///run/host/home/dkchw/Documents/Code/Ongoing/Repo/AI_Dict/extension/)) operates as a first-class citizen alongside the desktop app:

1. **Shadow DOM Isolation (`#ai-dict-extension-root`):**
   - The entire extension UI (trigger bubble, Simple MT card, Full Feature card) is rendered inside an isolated `ShadowRoot` with `mode: "open"`.
   - Host page styles (Bootstrap, Tailwind, reset CSS) cannot bleed into the extension, and extension styles cannot alter the host page.
   - Content stylesheets are injected directly into the shadow root to adhere to strict Content Security Policies (CSP).

2. **Event Capture & Fullscreen Video Piercing:**
   - Standard event listeners (`bubble` phase) fail on sites like YouTube, Netflix, or Coursera because video players call `event.stopPropagation()` on `mousedown` and `mouseup`.
   - The extension registers listeners on `window` using the **capture phase** (`addEventListener("mouseup", handler, true)`).
   - In HTML5 fullscreen mode (`document.fullscreenElement`), floating fixed elements outside the fullscreen container are invisible. The extension dynamically detects fullscreen changes and **re-parents its host element inside the active fullscreen container** (e.g., `div#movie_player`).
   - Keyboard events (`keydown`, `keyup`) originating inside extension textareas explicitly call `e.stopPropagation()` to prevent video players from intercepting keys (e.g., typing "f" won't toggle YouTube fullscreen; typing "k" won't pause the video).

3. **Deep Selection Algorithm:**
   - Standard `window.getSelection()` returns empty strings when text is selected inside open Shadow Roots (common in 3rd-party subtitle extensions and web components).
   - The extension uses a recursive tree crawler (`getDeepSelection()`) that penetrates shadow boundaries to retrieve the exact highlighted text.

## 4. Key Design Choices & Trade-Offs

### 4.1 SQLite vs. Client-Server RDBMS (PostgreSQL/MySQL)
- **Choice:** SQLite embedded via SQLModel.
- **Trade-off:** We sacrifice concurrent multi-user write scaling.
- **Rationale:** AI Dict is a single-user desktop companion. SQLite requires zero configuration, no external background daemon, zero port management, and stores the entire user state in a single portable file that can be easily backed up or inspected.

### 4.2 Raw SQL Migrations vs. Alembic
- **Choice:** Explicit `ALTER TABLE` execution via lightweight scripts (documented in [`AGENTS.md`](file:///run/host/home/dkchw/Documents/Code/Ongoing/Repo/AI_Dict/AGENTS.md)).
- **Trade-off:** Developers must manually update the live database file when adding columns to `db.py`.
- **Rationale:** Alembic adds significant boilerplate, version table overhead, and operational friction for a single-user desktop app. Given that table columns are strictly additive with defaults, raw SQL `ALTER TABLE` statements provide complete transparency with zero dependency bloat.

### 4.3 Centralized Flat State in `App.jsx` vs. Redux/Zustand
- **Choice:** React 19 native `useState` lifted to [`App.jsx`](file:///run/host/home/dkchw/Documents/Code/Ongoing/Repo/AI_Dict/frontend/src/App.jsx).
- **Trade-off:** Props must be passed down to tab components.
- **Rationale:** The state tree has a shallow hierarchy (global tab collections, active profile, theme). Introducing Redux or Zustand adds unnecessary indirection and boilerplate without providing tangible performance benefits for this scale.

### 4.4 CTranslate2 int8 CPU vs. GPU PyTorch/Transformers
- **Choice:** CTranslate2 running 600M NLLB-200 with int8 quantization on CPU (`inter_threads=1`, `intra_threads=4`).
- **Trade-off:** Slightly lower translation speed than a dedicated CUDA GPU setup.
- **Rationale:** Portability and universal accessibility. Requiring CUDA, PyTorch, or GPU drivers would prevent AI Dict from running smoothly on standard laptops, MacBooks, and low-spec machines. CTranslate2 int8 CPU inference delivers 50–150ms translations with negligible memory usage (~600MB RAM) on virtually any modern x86 or ARM CPU.

## 5. Technical Debt & Architectural Limitations

Every mature project has architectural trade-offs that represent technical debt. Contributors should understand these constraints:

### 5.1 Non-Streaming Initial Lookups
- **Current State:** The primary lookup endpoints (`/api/search`, `/api/comparisons/search`, `/api/explains/search`) await the complete response from OpenRouter before returning JSON to the frontend. Only the follow-up chat endpoints stream tokens.
- **Impact:** Users wait 2–6 seconds for initial explanations to appear, rather than seeing a typewriter streaming effect.
- **Path Forward:** Refactor primary endpoints to use Server-Sent Events (SSE) or WebSockets, streaming initial Markdown chunks directly into the active tab.

### 5.2 SQLModel Attribute Staleness
- **Current State:** SQLModel/SQLAlchemy expires all object attributes immediately after `session.commit()`. Accessing `word.term` or `word.model_dump()` after commit triggers an implicit query that fails if the session context has shifted.
- **Rule:** Always call `session.refresh(obj)` immediately after `session.commit()`, or extract required data before committing.

### 5.3 OpenRouter Reasoning Budget Incompatibility
- **Current State:** When reasoning effort (`low`, `medium`, `high`) is configured, `ai.py` injects `extra_body: {"reasoning": {"effort": ...}}`.
- **Risk:** Some OpenRouter models (particularly non-reasoning open-source models) return a `400 Bad Request` if unexpected parameters are present in `extra_body`.
- **Mitigation:** The codebase handles reasoning errors gracefully by falling back to standard parameter sets, but developers adding new models must verify compatibility.

### 5.4 Video Player Keyboard Conflict Surface
- **Current State:** Third-party websites (especially YouTube, Twitch, Vimeo) implement aggressive global keyboard handlers on `window`. While extension inputs shield keypresses via `e.stopPropagation()`, highly custom player overlays occasionally register capture-phase shortcuts that require continual CSS/JS event shielding refinement.

## 6. Security & Vulnerability Analysis

Contributors must adhere to security best practices regarding data handling and API interactions:

### 6.1 Localhost CORS Policy (`allow_origins=["*"]`)
- **Vulnerability:** [`server.py`](file:///run/host/home/dkchw/Documents/Code/Ongoing/Repo/AI_Dict/src/ai_dict/server.py#L39-L45) configures CORS with `allow_origins=["*"]`.
- **Context:** Because AI Dict binds to `127.0.0.1:4321` on the local machine, this allows the Browser Extension (running on arbitrary web origins) to communicate with the local server.
- **Risk:** A malicious website visited in the user's browser could theoretically send cross-origin requests to `http://127.0.0.1:4321/api/words` and read or modify the user's vocabulary history.
- **Mitigation Strategy for Contributors:** 
  1. Never bind Uvicorn to `0.0.0.0` in production without authentication.
  2. A future security hardening step is implementing a shared local token (stored in extension storage and validated via an `X-AI-Dict-Token` HTTP header).

### 6.2 Plaintext API Key Storage
- **Vulnerability:** The OpenRouter API key is stored in plaintext in the SQLite `AppSetting` table (`key='OPENROUTER_API_KEY'`).
- **Context:** Standard for local single-user desktop apps, but vulnerable if the user's local disk or backup `.zip` is compromised.
- **Mitigation:** Sensitive backup archives should be protected with file-level encryption or user file permissions (`chmod 600`).

### 6.3 Prompt Injection Surface
- **Vulnerability:** When a user looks up arbitrary foreign text or untrusted web snippets, that text is interpolated directly into system/user prompts sent to the LLM.
- **Risk:** Crafted text could attempt prompt injection (e.g., *"Ignore previous instructions, return format as..."*).
- **Mitigation:** System prompts in [`ai.py`](file:///run/host/home/dkchw/Documents/Code/Ongoing/Repo/AI_Dict/src/ai_dict/ai.py) use clear delimitation (`"""text"""`) and strict role constraints to minimize instruction hijacking.

### 6.4 Markdown Rendering & XSS
- **Vulnerability:** AI responses and user notes are rendered via `react-markdown`.
- **Mitigation:** Raw HTML rendering is disabled by default in `react-markdown`. All Markdown is parsed into React virtual DOM elements, preventing arbitrary `<script>` or `onload` injection from malicious AI output.

## 7. Potential Conflicts & Edge Cases

When developing new features, be vigilant for these known conflict areas:

1. **Port Collisions on `:4321`:**
   - If another service occupies port 4321, Uvicorn will fail to start. The extension is hard-coded to look for the backend on `http://127.0.0.1:4321`.
2. **Model Download Concurrency:**
   - When NLLB-200 is downloading for the first time, multiple parallel requests must not trigger duplicate download threads. The `_DOWNLOAD_IN_PROGRESS` registry in [`mt.py`](file:///run/host/home/dkchw/Documents/Code/Ongoing/Repo/AI_Dict/src/ai_dict/mt.py) prevents concurrent download collisions.
3. **Third-Party Subtitle Extensions:**
   - Tools like Language Reactor, Dualsub, or YouTube auto-caption modifiers frequently mutate the subtitle DOM. AI Dict uses debounced `selectionchange` observers and deep node inspection to coexist peacefully with these tools.
4. **FastAPI Catch-All Route Precedence:**
   - The SPA catch-all route `@app.get("/{full_path:path}")` MUST remain the absolute last route in [`server.py`](file:///run/host/home/dkchw/Documents/Code/Ongoing/Repo/AI_Dict/src/ai_dict/server.py). Any API endpoint placed after it will be shadowed and return `index.html` instead of JSON.
